## 本机 HTTP 负载样本

[原始报告](../reports/load-20261104T035926232657Z.json)：64 个客户端工作线程，单个本地服务进程，应用并发槽 32，SQLite WAL / synchronous FULL，实际发送 **2,450 个 HTTP 请求**。客户端与服务端在同一台电脑，HTTP 新连接和线程调度都计入延迟。客户端为持续补充任务的并发池，不代表 2,450 请求在同一瞬间抵达。

| 阶段 | 请求数 | 实际结果 |
|---|---:|---|
| 同房型连续三晚争抢 | 600 | 40 个 201 成功、53 个 409 无房、507 个 503 |
| 同一键重试 | 200 | 105 个 200 返回原订单、95 个 503 |
| 相同键更改数量 | 50 | 50 个 409 幂等冲突 |
| 单次数量超上限 | 60 | 60 个 400 |
| 四批混合日期/房型/数量 | 640 | 21 个 201、214 个 409、405 个 503 |
| 并发重复取消 | 100 | 41 个 200、59 个 503；成功响应含幂等返回 |
| 回补后再抢同房型 | 200 | 20 个 201、30 个 409、150 个 503 |
| 浏览房态 | 600 | 600 个 200 |

每阶段及最终对账均通过，无 transport_error、无 500。初始热点房量为 40，首次恰好成功 40 单；取消 20 单后，补售恰好成功 20 单。重复取消阶段结束后，通过服务层逐一确保目标 20 单已取消，再开始补售；该清理调用**不计入 HTTP 吞吐量**，原始报告已标记。

总体状态分布为 **201:81、200:746、400:60、409:347、503:1,216**。过载拒绝响应占 49.63%，因此本轮结果不能被描述为“2,450 单都处理成功”。本项目的正确性目标允许明确拒绝请求，但绝不接受超卖或静默丢单。

热点争抢阶段总响应速度约 331.70 次/秒，p95 514.02 ms，其中新建成功订单 40 笔 / 1.8089 秒，约 22.11 笔/秒。浏览阶段约 526.33 次/秒，p95 136.96 ms。原始报告的 completed_rps 包含业务拒绝和过载响应；不能把它当作成功预订吞吐量。不同负载阶段速度差异明显，且样本没有预热、重复轮次或置信区间，不用于承诺 SLA。

## 可复现与性能边界

~~~powershell
Set-Location -LiteralPath 'E:\Projects\hotel-reservation-lab'
.\scripts\run.ps1 scripts.verify
.\scripts\run.ps1 scripts.load
.\scripts\run.ps1 scripts.reproduce
~~~

每次压测使用新的独立测试库，不使用基线 1,192 笔演示订单库。场景夹具包括 1 家模拟酒店、3 类房型、2,000 客户、7 天房态；容量分别 40、25、12。数据规模和初始容量由 scripts/support.py 固定，负载顺序由 scripts/load.py 固定；线程调度和每阶段 503 数量会随机器负载变化，不能要求字节级复现性能结果。

默认高并发为受控 64 个客户端和 8 个 OS 进程，**没有进行百万请求、数千进程或公网流量测试**。它检验重叠请求、明确过载和事务不变量。没有测试分布式部署、PostgreSQL 行锁/隔离级别、网络分区、磁盘写满、断电、支付回调、异地多活或真实身份认证。

当前缺少可用 PostgreSQL 驱动/实例；没有安装或连接线上服务。未来若授权并提供真实实例，再单独实现 PostgreSQL 存储层和迁移，并在真实实例重跑功能/压力测试。此项目已完成的 SQLite 版本可以独立运行，此限制不会隐藏为“已完成 PostgreSQL 验证”。
