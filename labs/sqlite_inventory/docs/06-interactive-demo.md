# 本机交互式酒店演示

此页面是独立的合成数据实验台，与销售演示分开；不读取既有酒店运行库。每轮创建一个新的 .runtime/interactive-hotel/<run-id>/hotel.db，运行结束保留 result.json。不会清理或覆盖旧数据。

## 启动与使用

~~~powershell
Set-Location -LiteralPath 'E:\Projects\hotel-reservation-lab'
.\scripts\run.ps1 hotel.demo --port 8092
~~~

在浏览器打开 **http://127.0.0.1:8092/**，使用打印出的精确127.0.0.1地址，不使用localhost或外部域名。前台启动时用Ctrl+C停止，建议先等当前一轮完成。端口被占用会报错，不会停止占用该端口的其他程序；可自行改为8093。

页面可调每日房量、首轮请求数、并发线程、每单间数、入住与退房日、取消目标单数和补售请求数。日期区间包含入住日、不包含退房日。点击运行后实时轮询实际事件；运行很快时可能首次刷新就已结束，没有人为制造播放延迟。

默认案例：8间、24个首轮请求、8并发、每单1间，取消前3笔成功订单，再发10笔补售请求。预期首轮8单成功16次无房，取消3单后补售3单，其余补售无房，最终剩余0。实际结果以页面事件和对账为准。

## 真实执行与示意的边界

- 浏览器通过演示API发起一轮任务，服务端有限线程池直接调用当前 Store 业务事务。是真实 SQLite 预订和并发线程，不是浏览器同时发送N个下单HTTP请求，也不等同于已有HTTP压力测试。
- 首批任务用线程屏障共同起步，记录实际重叠尝试峰值与真实线程ID；这不意味着数据库同时有多个写事务。
- “write_lock_acquired”在原业务事务的BEGIN IMMEDIATE实际返回后记录；“transaction_committed”在真实提交成功后记录。写锁使SQLite写事务串行。
- “attempt_started”仅表示线程进入业务调用，不表示拿到锁；事件序号是应用观察顺序，不是数据库全部内部调度的日志。
- 每批完成后读取稳定房态并对账；页面的逐晚库存来自实际数据库，不是根据计数器画出来的预测。
- 自动执行4次同键重放；每个取消目标重复取消2次，展示幂等不会重复扣房/回补。
- 流程说明明确标为示意。代码按钮读取当前项目的白名单函数，并显示真实起始行号：hotel/service.py 的 transaction、reserve、cancel、nights。

## 有界与隔离

| 项目 | 上限 |
|---|---|
| 首轮请求 | 1–80 |
| 实际业务线程 | 1–12 |
| 每日房量 | 1–30 |
| 每单房量 | 1–3 |
| 住宿区间 | 2027年内1–7晚 |
| 取消目标 | 0–10笔已成功订单，每单重复2次 |
| 补售请求 | 0–30 |
| 每轮业务调用总数 | 最多134次 |
| 每服务进程轮数 | 最多20轮，重启不会删除旧记录 |
| 同时运行轮数 | 1 |
| HTTP连接线程 / 排队 | 固定4 / 最多8 |
| HTTP排队 / 总读取期限 | 0.5秒 / 2秒 |
| 演示输入正文 | 最多4 KiB |
| 事件记录 | 每轮最多1,000条 |

仅绑定127.0.0.1；Host和Origin校验、每次服务随机令牌、页面CSP和固定代码白名单阻止任意来源调用和任意文件读取。令牌由本机页面加载并放在请求头，不放URL。没有上传入口、任意SQL、任意数据库路径、真实账号或外部服务。

这是本机合成数据演示，不是面向公网的认证系统。拥有本机进程权限的程序仍能访问本地页面；没有声称抵御本机恶意软件。有限轮数不等于长期磁盘配额，运行记录保留在项目内，不自动删除。

## API与代码

GET / 提供页面；POST /api/runs 启动新轮，返回202与随机run-id；GET /api/runs/{id}读取真实事件和状态；GET /api/source/{symbol}读取固定函数。API要求页面令牌。忙碌时503 demo_busy表示新轮未启动；会话轮数满返回429。参数无效时在创建目录前拒绝。

实现：hotel/demo.py；页面：hotel/demo.html；验证：tests/test_demo.py。核心预订逻辑与表结构未修改。TracedStore只围绕原事务管理器记录锁取得、提交和失败，不替换事务SQL。
