# 有界 HTTP 过载保护与纯 HTTP 端到端验证

当前版本把连接处理改成固定线程池和有界队列。**31 项功能检查全部通过**，其中包含真实 HTTP 客户端等待 Retry-After 后按同键重试；五级并发各两轮的库存、幂等承诺和资源上限检查通过，纯 HTTP 取消与补售链路通过。没有设定性能 SLO，也没有生产容量结论。

功能证据：[31项结果](../reports/functional-20261104T043355786068Z.json)、[逐项日志](../reports/functional-20261104T043355786068Z.txt)。分阶段证据：[最新实测 JSON](../reports/bounded-http-20261104T043224232615Z.json)。

## 连接与排队怎么限制

~~~mermaid
flowchart LR
    TCP[TCP 接收器] --> Q{固定长度 FIFO 队列}
    Q -->|队列满| R[503 server_busy]
    Q -->|排队超时| E[503 queue_wait_timeout]
    Q --> W[固定 N 个连接工作线程]
    W --> H[请求头和请求体绝对读取期限]
    H --> DB[SQLite 原子事务]
    DB --> O[订单结果或明确错误]
~~~

| 边界 | 默认运行参数 | 本次阶段实验参数 |
|---|---:|---:|
| 连接工作线程 N | 8 | 8 |
| 等待队列 Q | 32 | 16 |
| 排队有效期 | 1 秒 | 0.5 秒 |
| 请求头与请求体绝对读取期限 | 3 秒 | 3 秒 |
| 响应写入及拒绝连接关闭预算 | 0.25 秒 | 0.25 秒 |
| 拒绝连接丢弃未读数据上限 | 64 KiB | 64 KiB |
| JSON 请求体上限 | 16 KiB | 16 KiB |
| SQLite 写锁等待期限 | 5 秒 | 5 秒 |

队列包含尚未交给工作线程的已接受连接；不为每个连接新建线程。接收循环检查排队过期，工作线程取出任务时再次检查。请求读取期限从工作线程开始处理连接计时，每次底层 recv 重新计算剩余时间，持续滴入少量请求头也不会无限续期。请求头超时可直接断开；请求体读取超时返回 408，不执行预订服务。

应用层工作线程数不超过 N，队列不超过 Q；进程内已接受、尚未关闭的连接峰值不超过 N+Q+1，其中 1 是单接收器正在拒绝的瞬态连接。过期队列清理也由接收循环执行，不增加按连接增长的线程。这不包含内核待 accept 队列、TCP 缓冲、TIME_WAIT 或客户端线程，不代表操作系统全面抗过载能力。

队列过期由检查触发；拒绝响应写入和操作系统调度可能推迟实际响应送达。读期限只覆盖读取请求，不是“连同数据库事务在内的总响应 SLA”。健康检查共用接入队列，也可能在过载时被拒绝。此服务仍为仅监听本机的教学后端。

## 503 与重试语义

| 错误字段 | 含义 | 数据库效果 |
|---|---|---|
| server_busy | 等待队列已满 | 未进入业务 |
| queue_wait_timeout | 排队时限已过 | 未进入业务 |
| server_shutdown | 关闭期间不再开始排队业务 | 未进入业务 |
| database_busy | SQLite 写锁等待超时 | 事务已回滚 |

上述 503 都带 Retry-After: 1 以及 retryable=true、outcome=not_committed。必须至少等待响应指定的间隔，再以同一客户、同一幂等键和相同预订参数重试；可追加少量随机退避并限制尝试次数。取消重复相同订单 ID 与客户即可。不要为同一次意图每次换新键。

性能阶段不自动重试，防止隐藏拒绝率。端到端测试客户端最多尝试 4 次，记录每一次实际 HTTP 请求和整个逻辑操作耗时。功能测试另外强制制造一次 503，验证客户端至少等 1 秒、随后以原键成功、再次重放只返回同一订单。

没有完整 HTTP 响应的网络错误，或一般 500，不属于“已知未提交”的保证范围；可能需要同键重试或查回。409 sold_out / idempotency_conflict 不进行自动技术重试。输入错误也不应靠重试解决。

每轮、每级并发使用全新合成库：2,000 客户、3 类房型、7 天日历；测量房型每日容量 170，发起 160 个有效且幂等键唯一的单间三晚预订，排除“无房”对接纳率的干扰。客户端与服务器同机，HTTP 新连接、排队和网络栈等待均计入客户端延迟。每个并发等级执行两轮，没有预热或开放环到达率控制。

十阶段共测量 1,600 个预订请求：**985 个新订单成功响应、615 个 server_busy、0 个连接错误、0 个 database_busy、0 个未确认提交**。每阶段另做 1 次恢复健康检查，均为 200。所有阶段对账通过，观测峰值工作连接 8、排队 16、已接受连接 25；关闭后工作线程均为 0。没有在这些阶段观察到排队过期，但功能测试专门强制验证了该路径。

96 并发阶段的成功率高于 32，并不能证明容量随并发提高：固定并发池不等于固定到达速率，TCP 待连接和拒绝响应节奏都会改变实际提交顺序；本样本没有足够指标证明某个单一原因。这里不计算或宣称生产吞吐容量。高并发下 503 比例仍高，意味着大量客户当次没有获得业务完成；正确性通过不代表服务可用性达标。

## 纯 HTTP 取消与补售

所有订单创建、取消、订单查询和房态查询都经过真实本机 HTTP。初始夹具只插入客户、房型和日历；之后 **服务层直接修改业务的调用数为 0**，不存在原负载脚本的取消补齐。

| 阶段 | 实际 HTTP 次数 | 结果 |
|---|---:|---|
| 首轮争抢 20 间 | 80 | 20 单创建，60 个 sold_out |
| 对其中10单各重复取消4次 | 40 | 全部 200，含幂等返回 |
| 逐单查询10个目标订单 | 10 | 全部明确为 CANCELLED |
| 查询释放后的房态 | 1 | 连续三晚均恢复10间可售 |
| 再次补售 | 50 | 恰好10个新订单，40个 sold_out |
| 最终查询房态 | 1 | 区间剩余0 |

此链路共 182 次实际请求，本轮无需重试；每阶段及最终对账通过。它与十个阶段测量及10次健康检查合计 **1,792 次实际 HTTP 请求**。逐请求日志保留各逻辑操作、每次尝试、订单 ID、状态及延迟。业务最终状态由 HTTP 查回确认，库存一致性另用只读数据库审计核验。
