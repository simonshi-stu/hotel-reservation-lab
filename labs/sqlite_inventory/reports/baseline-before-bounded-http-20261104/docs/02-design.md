# 事务与并发设计

## 一个预订请求经过什么

1. HTTP 层验证 JSON 对象、字段集合、请求体长度。业务层检查客户/房型/键、日期和数量。
2. 新建数据库连接，启用外键，设置同步写入 FULL；写操作使用 BEGIN IMMEDIATE。
3. 在写事务内检查 (customer_id, idempotency_key)。已存在且参数一致则返回同一订单的当前状态；参数不同返回 409。
4. 按日期取完整日历，确认所有夜晚存在且 available ≥ quantity。不存在返回 404，房量不足返回 409。
5. 创建 CONFIRMED 订单，对每个占用夜条件扣房，创建价格快照和负向流水。
6. 同一事务提交；SQL 失败、约束失败或任一晚不足都回滚整单。

**入住区间是 [check_in, check_out)**。1-30 晚，每单 1-10 间；有房型没有对应日历不视为零房，单独返回 inventory_not_found。所有金额为整数分，价格由服务端逐晚求和。

## 为什么不会超卖

SQLite WAL 允许读取快照，但同一文件同一时刻只有一个写事务。BEGIN IMMEDIATE 在读取库存前争取写锁，因此不同 HTTP 线程、不同 Python 进程都不能先读到同一库存后各自成功扣减。条件 UPDATE 的 available≥quantity 和数据库 CHECK 是第二层约束。锁争用超过 5 秒返回 503 database_busy，要求相同键重试。

锁来自数据库，不依赖进程内 Python Lock。代价是写入串行化，跨日期甚至不同酒店也会竞争全局写锁。这适合实验与小规模本地运行，不能据此宣称高吞吐的分布式酒店平台。

房态查询是只读快照，结果可能马上过期。服务不承诺“查到房就一定下单成功”。订单状态、逐晚扣房、流水一起提交，避免有订单没扣房或扣了第一晚而第二晚失败。

## 幂等与取消

- 唯一键为客户 + 幂等键。相同客户、相同参数返回同一 ID，初次 201，成功重放 200。
- 键相同但房型/日期/数量不同返回 409 idempotency_conflict。
- 只持久化成功订单的幂等键；sold_out、busy 等失败未占用键，取消释放房量后同一个失败键可能成功。
- 已取消订单使用原键重试仍返回 CANCELLED，不会重新扣房；重新预订需新键。
- 取消在同一写事务内验证客户归属，读订单状态，只对 CONFIRMED 按逐晚记录回补，写正向流水，再设 CANCELLED。
- 重复取消返回当前 CANCELLED；多线程同时取消只有一个事务实际回补。
- 不存在支付超时、待支付占房、自动过期、改期、入住或退房状态。取消表示取消预订，不是实际退房。未来增加支付回调需要明确独立状态机和键。

唯一键只能保证已提交记录的业务去重，不保证网络“恰好一次传输”。客户端若在提交后断线，用原键重试可找回该单。

## 对账

Store.audit 在一个读取事务中核验：

~~~text
每个房型、每晚：
available = capacity - Σ(CONFIRMED 订单逐晚 quantity)
available = capacity + Σ(库存流水 delta)
~~~

同时检查订单晚数、日期边界、逐晚数量/房型、总价，逐晚 BOOK/CANCEL 流水与状态是否匹配，外键和 SQLite integrity_check。测试会故意删除流水，确认对账能识别异常。预订/取消的第二晚触发 SQL 错误时，分别验证整个写事务回滚；也用独立进程在未提交写入后强制退出，验证 SQLite 恢复。

## HTTP 与过载

| 方法与路径 | 功能 |
|---|---|
| GET /health | 本地健康响应，标注 synthetic=true；不执行数据库完整性检查 |
| GET /availability?room_type_id=…&check_in=…&check_out=… | 逐晚房态、区间瓶颈房量与一间总价 |
| POST /reservations | 创建或幂等返回订单，字段见 README |
| GET /reservations/{id}?customer_id=… | 查询属于该客户的订单 |
| POST /reservations/{id}/cancel | JSON customer_id，幂等取消 |

错误类别：400 输入无效；404 客户、订单或日历缺失；409 无房或幂等冲突；415 内容类型错误；503 应用并发槽满或数据库写锁超时。503 带 Retry-After: 1，压测不自动重试，避免隐瞒失败。

本机 server 默认允许 32 个应用操作同时执行，超过即 503 server_busy；单请求体最大 16 KiB，读取超时 5 秒。该限制不等于总 TCP 连接数/线程数限制：标准库 ThreadingHTTPServer 仍按连接创建线程，属于教学服务。无真实认证、授权令牌、TLS 或公网流量治理，仅监听 127.0.0.1。

## 面试讲解建议

先说业务不变量：同房型每天不能卖过 capacity，多晚订单必须全部成功或全部失败。然后用“第一晚有房、第二晚无房”解释为何不能拆成多个事务。再用“双进程都查到最后一间”解释为何库存读取也要在写事务内。

接着讲客户范围幂等键和“提交成功但网络断开”的重试；取消必须与库存回补在同一事务。最后展示 8 个 OS 进程测试、故障注入和独立对账，而不是仅展示 HTTP 200。

诚实说明局限：当前 SQLite 单写者。迁移 PostgreSQL 时应按 (room_type_id,stay_date) 一致顺序锁住所有占用夜，处理唯一键冲突与死锁重试，并在真实驱动/实例上重新验证；不能简单替换连接字符串，也不能把当前测试冒充 PostgreSQL 验证。
