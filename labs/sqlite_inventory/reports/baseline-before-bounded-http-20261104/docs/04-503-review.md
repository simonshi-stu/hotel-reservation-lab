# 1,216 次 503 的独立复核

**结论：这 1,216 次响应全部是应用并发槽满导致的 server_busy；当次请求没有进入业务服务。它们不是成功订单，也不是正常无房的业务拒绝。本轮证明了所检查的库存一致性，没有证明系统达到任何可用性或吞吐量目标。**

依据为原始负载报告 load-20261104T035926232657Z.json、hotel/api.py、hotel/service.py、scripts/load.py；并额外运行 scripts.review_503，在独立新库验证拒绝前后数据库不变、同键稍后可成功、连接线程不受应用槽约束。复核原始测试库最终为 81 笔订单，其中 20 已取消、61 有效；库存、订单和流水对账通过。复核未修改原始报告或原始负载数据库的数据。

## 按请求类型重算

| 请求类型 | 请求数 | 创建或成功返回 | 正常业务/输入拒绝 | 503 未进入业务 |
|---|---:|---:|---:|---:|
| 新键预订：热点、四批混合、回补后抢房 | 1,440 | 81 个 201 新建订单 | 297 个 409 sold_out | 1,062 |
| 原订单同键重试 | 200 | 105 个 200，同一订单 | 0 | 95 |
| 同键改参数 | 50 | 0 | 50 个 409 idempotency_conflict | 0 |
| 单次数量超限 | 60 | 0 | 60 个 400 invalid_quantity | 0 |
| 重复取消 | 100 | 41 个 200，含幂等返回 | 0 | 59 |
| 房态浏览 | 600 | 600 个 200 | 0 | 0 |
| 合计 | 2,450 | 827 个 2xx 响应 | 407 个业务/输入拒绝 | 1,216 |

827 个 2xx 中只有 81 个是新建订单，不能把查询、取消、重放全部计为下单。所有请求的过载拒绝率为 49.63%；只看新键预订，1,062 / 1,440 = **73.75% 因过载被拒绝**，81 / 1,440 = 5.625% 创建成功；还有 297 个确实因无房拒绝。这个分母更接近用户尝试下单的体验。

新建订单中的混合房型订单可能订多间，81 笔订单不等于 81 间房；不能混用订单数、房间夜和请求数。

## 503 从哪里产生

HTTP 处理器在解析路由、读取 JSON 和调用 Store 之前，执行 BoundedSemaphore(32).acquire(blocking=False)。64 客户端线程持续补充请求，应用操作到达上限时立刻返回 503 server_busy 和 Retry-After: 1，不入队重试。这个返回分支没有调用 reserve 或 cancel。

进入应用槽后，预订、幂等重放和取消均使用 SQLite BEGIN IMMEDIATE。SQLite 同一文件只有一个写事务，等待写锁的请求也占着应用槽；同步写入 FULL 和响应发送也在槽内。因此并发写入容易耗尽 32 槽。这是代码层面合理的机制解释，**原样本没有采集逐请求锁等待和 CPU/磁盘指标，不能断定硬件、磁盘或某一条 SQL 是实测主瓶颈**。

另一个 503 来源为 database_busy，即超过 5 秒的数据库写锁等待；本次原始报告中该错误计数为 **0**，不能将 1,216 误解为数据库锁超时。线程池数 64 和槽数 32 也不决定精确拒绝数，实际数量由请求耗时、调度与到达顺序决定。

## 对业务的影响

- 新键预订收到 server_busy 时，不创建订单、不扣房，也不占用幂等键。客户需要稍后用相同参数和相同键重试；本轮压测没有自动重试，因此这些请求当次未完成。
- 已有订单的同键重试被拒绝，并不意味着原订单消失；只是该次查回结果没有完成。原订单状态须由成功查询或同键重试确认。
- 取消请求被拒绝时，当次不回补房量；若其他重复取消已经成功，同单仍可能已取消。不能按 59 个失败响应推断 59 个订单未取消。
- 原报告只保存阶段聚合，没有保存每个取消响应对应的订单 ID，因此无法从 41 个 200 推断 HTTP 实际取消了多少个不同订单。
- 原负载脚本在取消阶段后，直接调用服务层确保 20 个目标订单都已取消，再开始回补后抢房。因此“20 间回补后又售出 20 间”是事务及库存正确性证据，**不是纯 HTTP 取消链路全部完成的证据**。

独立探针用一个应用槽：主动占满后分别请求创建、取消和健康检查，三者均 503；数据库订单数、流水数和剩余房量完全不变。释放槽后，使用刚才被拒绝的同键预订成功创建，取消也成功。探针只支持“server_busy 分支没有业务写入”的结论，不代表任意网络超时或其他 503 都没有提交；对提交结果不明的网络失败仍需幂等查回。

## 过载保护、业务未完成和缺陷分别是什么

| 类别 | 本次可确认的事实 | 判断 |
|---|---|---|
| 过载保护 | 应用槽满时明确返回 server_busy，没有静默成功或负库存 | 该分支符合设计 |
| 业务未完成 | 新键预订有 1,062 次在入业务前拒绝，取消另有 59 个拒绝响应 | 客户当次请求未获完成；不能计作业务成功 |
| 可用性限制 | 相同槽同时覆盖写请求、只读请求及健康检查；等待锁和发响应也占槽 | 可造成更广泛拒绝，尚无可用性目标或公平性保证 |
| 已复现的资源保护缺口 | 应用槽为 1 时，两个只发送部分请求头的连接已创建两个工作线程，应用槽仍空闲 | 并发槽不限制连接/线程总数，不能声称完全防止进程/线程耗尽 |
| 请求头超时缺口 | settimeout 在 dispatch 内，晚于标准库请求头解析；部分请求头在进入该设置前等待 | 当前教学 HTTP 服务不适合暴露公网 |
| 验证缺口 | 负载断言允许 503，多个阶段无最低接纳率；未保留逐请求结果，取消有服务层补齐 | passed=true 只表示现有正确性断言通过，不表示可用性达标 |

资源保护缺口由两条受控本机连接复现，没有大规模耗尽系统资源。当前交付保留原实现与历史报告，清楚披露这些限制；尚未新增连接级有界工作池、请求头读取期限、公平排队、客户端退避重试或纯 HTTP 端到端取消完成率测试。

## 可以说与不能说的结论

可以说：本机 SQLite 版本在受控并发和故障测试中保持所检查的库存不变量；32 个应用槽触发明确过载拒绝；原始响应已完整分类。

不能说：2,450 单全部成功、64 客户端可稳定承载、总响应速度就是成功下单吞吐量、库存正确就意味着高可用、已经验证 PostgreSQL 或生产环境。

容量评估仍需要单独确定业务成功率/延迟目标，提供足够库存减少无房干扰，记录逐请求业务结果与唯一订单数，测量排队/锁等待，进行重复的稳态阶梯负载，并覆盖真实客户端重试和纯 HTTP 取消链路。没有这些证据，本报告不给出吞吐容量结论。
