# 两条酒店开发路线的整合说明

## 结论

这不是“本机版本整体比 GitHub 新”。两边实现粒度不同，应保留互补能力，而非互相覆盖。本次将本机完整源码、合成数据、实验记录及文档纳入 `labs/sqlite_inventory/`，保留原 GitHub 的 `hotel_sim/`、`hotel_demo/` 和所有测试。

| 范围 | 主应用：hotel_sim / hotel_demo | 策略实验室：labs/sqlite_inventory |
|---|---|---|
| 库存粒度 | 具体房号 × 日期；全程同一房间 | 房型/床型 × 日期；全程同一房型 |
| 加床与婴儿床 | 儿童年龄、固定床位、每房限制和每日资源库存 | 未实现，不可从另一版本借用验证结论 |
| 策略 | 严格房型、升级、保护库存升级；升级预算 | 三种策略；有界贪心调整已有订单、SAVEPOINT 失败回滚 |
| 持久化 | SQLiteStore、幂等记录、取消、恢复查询；纯 Allocator 单独使用仅为内存对象锁 | SQLite 库存事务、幂等、取消、固定线程池及有界 HTTP 排队 |
| 已有订单调整 | 本模块未引入策略实验室的搬移算法 | 仅按日期重叠、房型与升级同意筛选；没有“未入住状态”过滤 |
| 价格语义 | 显式升级差价及预算 | 免费升级、锁定原订单价格 |

## 如何运行

从仓库根目录运行：

```powershell
python -B scripts/verify_integrated.py --experiments
python -B -m hotel_demo.server --port 8019
```

主应用入口保持不变。房型策略实验室单独启动：

```powershell
Set-Location labs/sqlite_inventory
.\scripts\run.ps1 hotel.demo --port 8093
```

对应 `/planning` 页面及 `docs/07-room-planning.md`、`docs/08-policy-frontier.md`。本机默认 Python 路径保留，可用进程变量 `HOTEL_PYTHON` 指向已安装解释器。统一验证入口使用当前 Python 启动子进程，隔离两套 scripts/tests 导入及数据库；临时文件和报告保留在当前 E 盘项目目录，不安装依赖。

## 证据边界

原 4 组、712 笔需求实验只属于房型策略实验室。严格/自由升级/保护升级接受 243/282/247 单、售出 586/673/601 间夜，不能描述为“同时验证具体房号、加床、婴儿床、已入住状态和 PostgreSQL”。零违规仅指该实验实现的校验范围。模拟收益不是实际营收。

主应用的加床、婴儿床与全程同房由自身测试和 `scripts/audit_invariants.py` 验证，不将其请求数或规则拼接到 712 笔结果中。

本次完成的是代码与验证工作流整合，不是把两个数据库直接合成一个数据库，也不是让主应用自动搬移已有订单。若将来统一分配内核，必须先统一儿童年龄/人数、同房/同房型、价格与升级授权、入住状态、资源释放和跨进程事务语义，然后重新实验；旧结果不能沿用。

## 统一启动接口（并非统一数据库）

```powershell
python -B scripts/run_hotel.py room --port 8019
python -B scripts/run_hotel.py type --port 8093
```

同一个命令明确选择模型，自动配置独立工作目录、E 盘临时目录和页面地址。两条命令可在不同终端运行；不把同一数据库同时交给两个服务。选 `room` 查看具体房间、加床和婴儿床；选 `type` 查看 `/planning` 的房型策略及搬移实验。原入口全部继续可用。

尚未融合的功能：具体房间引擎不能自动使用房型引擎的旧订单调整；房型引擎不能借用另一引擎的加床资源校验。完整融合需新增持久化入住状态、同房搬移规则及资源预留流水，在同一个 SQLite 写事务内校验并迁移全部受影响房晚、加床与婴儿床，再做故障回滚、幂等恢复和跨进程竞争验证。本次没有进行上述行为或数据库迁移。
