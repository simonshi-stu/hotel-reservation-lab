# 优先级任务调度教学实验

## 来源与范围

来源是项目所有者提供的 Python `heapq` 抢占式调度题及规则确认。原讨论只有代码、示例和解释，**没有酒店测试运行证据**。本目录是 2026-11-14 新增并实际执行的独立教学实验，不是恢复出的历史酒店基准，不调用预订 API、不改库存或事务。

与酒店的关系仅是可用于讲解后台任务排队，例如可暂停的离线报表。不可直接把抢占式模拟用于数据库事务：真实预订必须保持事务完整性，不能按此例随意中断。多工作线程、重试、持久化、取消、超时和资源锁仍未实现。

## 规则

- 一个工作者、整数时间、正执行时长、零切换开销。
- 优先级数字越大越先执行；相同则先到达者优先，再按输入顺序。
- 抢占模式在新任务到达时重新选择；非抢占模式完成当前任务再选择。
- 输出完成顺序、执行时间段、完成时刻与等待时间。
- 无优先级老化；持续高优先级流量可能造成低优先级饥饿。本有限样本不证明公平性。

## 示例实测

| ID | 优先级 | 到达 | 执行时长 |
|---|---:|---:|---:|
| 1 | 3 | 0 | 1 |
| 2 | 1 | 1 | 3 |
| 3 | 2 | 2 | 1 |

抢占：`1 → 3 → 2`；时间段 `1:[0,1), 2:[1,2), 3:[2,3), 2:[3,5)`。
非抢占：`1 → 2 → 3`；时间段 `1:[0,1), 2:[1,4), 3:[4,5)`。

两种输出分别符合不同规则，原题隐藏测试为何失败仍不能凭此确定。原代码末尾只弹堆即可输出完成顺序，但如需完成时刻，必须累计剩余执行时间。本实现补足时间线，不声称是原题的唯一正确解。

## 复跑与验证

```bash
python -m scheduling_lab
python -m unittest discover -s tests -p test_priority_scheduler.py -v
```

本次执行 9 项测试通过，其中一项包含固定随机种子 `20261114` 的 **1,000 个合成案例**，与不用堆、每次推进一个时间单位的独立参考算法比较完成顺序及完成时刻，并核对每项任务总执行时长和非负等待时间。覆盖空队列、输入乱序、同优先级、同到达时间、完成边界和非法输入。1,000 个案例不是 1,000 个 unittest 测试，也不是真实访问量。

这是算法正确性实验，**不是 HTTP 并发压测、容量上限、真实酒店数据、抗重复预订攻击或生产验证**。相关 HTTP 实验单独见 [HTTP_BENCHMARK.md](HTTP_BENCHMARK.md)。
