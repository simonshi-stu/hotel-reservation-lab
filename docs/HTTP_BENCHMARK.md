# HTTP 并发实验：范围、结果与下一步

本实验只对脚本自己启动的 **127.0.0.1 临时服务** 发请求，不接受外部 URL，不接触现有演示数据库；每个并发档位新建独立临时库存并清理。数据全为合成数据，不代表酒店真实客流。

## 复跑

```bash
python scripts/benchmark_http.py
# 更短的开发检查
python scripts/benchmark_http.py --concurrency 1 4 --requests 16
```

默认并发 1/4/8/16/32，每档依次执行四阶段，每阶段 64 次 HTTP 请求：
1. 同一个请求键重复订三晚：最终只允许 1 条预订、1 个事件、3 间夜占用。
2. 重复取消同一订单：最终只释放一次库存、共 2 个事件。
3. 不同请求键竞争同一日期的标准房：4 间房成功、60 条业务拒绝，最后占用 12 间夜。
4. 并发读当前状态；每阶段结束核对真实 SQLite 数据，而不是仅看 HTTP 200。

脚本记录 HTTP 状态与业务状态，拒绝预订并非 HTTP 故障。传输超时记为 **UNCONFIRMED**，不自动重试，不能据此断言订单未创建。出现传输错误、非 200 响应或数据库断言失败，报告仍保存，进程返回非零。

## 2026-11-13 实测

基于 main 的 3f8eda7；云端 Linux / Python 环境见[原始结果](benchmarks/2026-11-13-loopback.json)。总计 1,280 次 HTTP 请求，无传输错误，所有阶段数据库核对通过。

| 并发客户端 | 同键预订吞吐（次/秒） | 同键预订 p95（ms） | 不同键抢房吞吐（次/秒） | 不同键抢房 p95（ms） |
|---:|---:|---:|---:|---:|
| 1 | 152.60 | 8.50 | 96.80 | 29.16 |
| 4 | 142.19 | 37.51 | 130.24 | 34.13 |
| 8 | 157.42 | 55.21 | 128.24 | 68.20 |
| 16 | 60.94 | 1024.53 | 60.66 | 103.63 |
| 32 | 59.15 | 1046.37 | 50.87 | 1069.98 |

**实际发现：增加并发不是自动增加吞吐。** 32 客户端下预订 p95 约 1 秒，吞吐低于低并发。服务内串行锁、连接排队与每次新建连接都可能影响结果；本轮未做组件剖析，不能直接归因于数据库，更不能推出生产容量上限。

**幂等不等于防攻击。** 重复相同键没有重复扣库存，但这些请求仍占用连接、线程与处理时间。不同键的恶意请求、慢连接、分布式流量均未验证。本版本未新增限流、认证或分布式防护。

## 边界与后续

- 这是短时、闭环、单服务进程、loopback 基准；客户端和服务端共享机器，无公网延迟。不是持续负载或独立压测机测试。
- 每个阶段启动成本计入阶段墙钟时间；单请求延迟从连接请求开始到响应解析完成，包含连接等待。p95/p99 用 nearest-rank 计算；小样本尾部波动大。
- 吞吐只统计收到 HTTP 响应的请求，不把超时算作完成；HTTP 200 的售罄拒绝仍属于完成请求。
- 尚未验证：持续压测、长期内存/线程增长、真实浏览器、多服务实例、生产数据库、恢复后的真实部署性能。
- 下一步应先剖析连接排队和串行临界区，再选择生产 HTTP 服务与有界并发；限流和预订过期要配合身份/业务规则设计，不能把本实验包装为抗攻击能力。
